## Traps

- **Two isolated-git-worktree builder agents running full test suites concurrently share the SAME physical Postgres test DB** (one Docker container on port 5434, not per-worktree) — each test file's `clean_db` fixture does a `TRUNCATE ... CASCADE` per test, so concurrent runs cause real, nondeterministic cross-process flakiness (different tests failing on repeated runs of the identical file). This is NOT a code bug — confirm no other pytest process is running (`ps aux | grep python`) before treating a flaky local test result as a real regression, and re-run once any concurrent agent's process has exited.
- **A command labeled `[MOVED] Use X instead` may not actually be redundant with X yet** — `/trade propose-cpu` carried that label pointing at `/trade propose`, but `propose`'s `counterparty` param was hard-typed to `discord.Member` with no team-code path ever built. Deleting it per the label would have removed the only way to trade with a CPU team. Before bulk-deleting anything tagged deprecated/`[MOVED]`, verify the claimed replacement actually has parity — don't trust the label.
- **Full-suite pytest runs can silently die if backgrounded or run with too short a timeout in this environment** — root cause never identified across multiple sweeps, DB-level causes ruled out. Workaround (unchanged from prior sweeps): split `tests/test_*.py` into ~2 batches, run each in the **foreground** with a long explicit `Bash` timeout (500s+), redirecting output straight to a file rather than piping through `tail`.
- **`ruff` is not on PATH / not in `.venv`** — use the absolute path `C:\Users\Owner\AppData\Local\Programs\Python\Python312\Scripts\ruff.exe` directly.
- **Driving the real `sim_orchestrator.sim_range`/`sim_until_rival` entry points in a test requires patching `services.sim_orchestrator.get_pool` locally** (`patch("services.sim_orchestrator.get_pool", AsyncMock(return_value=db_pool))`) — it is NOT in `tests/conftest.py`'s `_GET_POOL_PATCH_TARGETS` list (that list only covers modules previously exercised this way). A bare `MagicMock()` guild with `.get_channel = MagicMock(return_value=None)` and no `league_channels` rows seeded is sufficient to no-op every `_maybe_post_*`/announcer call cleanly (each independently fetches its own channel and returns early when absent) — see `tests/test_franchise_plan_service.py::test_fp1_pivot_fires_mid_call_against_real_sim_range` for the full working pattern, and `tests/test_playoff_sim_live_smoke.py` for the same pattern applied to `playoff_service.sim_series_game`.
- **`_should_pivot`'s returned `new_goal` value is a log-line label only, not the actual next goal.** `derive_and_persist_all` calls it purely to decide *whether* to pivot and to compose the `FRANCHISE-PIVOT` log message; the persisted `goal` always comes from a full, independent `derive_plan` re-run against the live record. For a win_now collapse this can land on `rebuild` rather than `_should_pivot`'s own `"transition"` label if the live record is bad enough (e.g. 0-30) — this is correct behavior (proves the re-derive is genuinely live-driven), not a bug. Don't "fix" the two to match without checking which one a test/doc actually needs.
- **10 pre-existing test failures are quarantined** via `@pytest.mark.xfail(strict=False)` (`test_setup_cog.py` ×8, `test_cpu_trade_acceptance.py` ×2), unchanged this sweep. A regression shows up as a NEW failure, not hidden inside these.
- See prior HANDOFF history (git log on this file, or session notes) for traps specific to the now-closed Plans A/B (rollover, coaching AI) sweeps — segfault-prone `with (...)` blocks in `conftest.py`, alembic drift under concurrent worktrees, Docker Postgres flakiness under heavy load. Still generally true of this environment; not re-hit this session.
- **Parallel isolated-worktree builder agents that each add a same-named new file will silently collide on merge if their internal helper functions share a name too.** Plan D's RA1 and RA2 builders both independently created `tests/test_role_service.py` with a same-named `_insert_league` helper but a *different signature/schema* (one with `salary_cap`, one with `current_phase`). Git's add/add conflict flags the file, but a naive "just concatenate both" resolution would leave the second definition silently shadowing the first at import time — tests written against the first helper's schema would then break in confusing ways. Rename the collision (e.g. `_insert_league_ra2`) during manual merge and re-run the combined file end-to-end before committing; don't trust that "no conflict markers left" means the merge is correct.
- **`derive_and_persist_all_for_team` requires an acquired `asyncpg.Connection`, not a bare `Pool`** (it calls `conn.transaction()` internally) — `async with pool.acquire() as conn:` before calling it, matching the pattern real call sites (`trade_service.py`) already use.
- **The `Phase` enum's declared order (`phase/states.py`) is NOT the real season-cycle adjacency graph.** `phase/graph.py`'s `NEXT_PHASES` (Plan E, PT1) had to diverge from a naive "next enum member" model in 3 evidenced places — rollover's draft-phase skip (from either `OFFSEASON_AWARDS_CLOSED` or `DRAFT_LOTTERY_DONE`), the playoff champion's awards-vote skip, and the `PROGRESSION_PENDING`/`WAIVERS_OPEN` loop-closing pair — confirmed by tracing every real `advance_phase` call site, not by reading the enum declaration order. Any future phase-graph work must re-verify against real call sites, not assume enum order is authoritative.
- **PT1 (the phase-graph validation gate) and PT4 (`sim_batch_hooks`'s missing re-check) had to ship in one atomic commit, not sequentially.** Landing PT1's gate alone would have turned the pre-existing silent phase-skip into a hard `PhaseError` crash on the very next real `/sim season` call, since the ungated hook's unconditional `advance_phase` call becomes illegal the instant the graph gate exists. Any similar "add a validation gate" + "fix a caller that would violate it" pairing in this codebase needs the same one-commit treatment.
- **Fixing a wrong unit/scaling bug in a value that's already rendered to users can surface a *second*, display-layer bug that a single-file plan scope won't catch.** Plan F's TB2 fixed `cpu_block_service.py`'s `asking_price` to stop applying a bogus `* 1_000_000` dollar-multiplier (confirmed no other `player_trade_value` call site scales it that way) — correct in isolation, but `bot/embeds/trade_embeds.py` renders that same field with a hardcoded `$` prefix shared with human-submitted (genuinely dollar-denominated) trade-block entries, so CPU-listed players now display implausibly tiny "asking prices" next to real dollar figures. Caught only because I read the embed/rendering layer during independent verification, not because the builder agent's plan scope included it (it was single-file-scoped to `cpu_block_service.py`). When a fix changes what a persisted field *means* (units, scale, semantics), grep for every place that field is rendered/displayed, not just where it's written — a "no bug found in this file" plan scope can still ship a real regression one layer up. **Resolved by Plan G** (`3e0cd46`) — user chose to hide the asking-price line entirely for CPU-generated entries rather than relabel or fabricate a dollar figure.
