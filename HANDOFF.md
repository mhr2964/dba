## Traps

- **A `with (...)` block with too many parenthesized context managers can segfault Python 3.12 under pytest.** `tests/conftest.py`'s `patch_get_pool` fixture used one giant `with (patch(...), patch(...), ...)` statement; growing it past 18 entries (adding a 19th patch target) crashed the Python process outright — reproduced deterministically (3/3 clean without the extra line, 3/3 crash with it, content-independent — an unrelated dummy patch line crashed identically — and reproduced under both Bash and PowerShell). A standalone script with the identical `with` block ran fine, so this is specific to pytest's assertion-rewrite recompilation of the file combined with CPython 3.12's codegen for long parenthesized `with` statements. Fixed by refactoring to a target-list + `contextlib.ExitStack` loop (`_GET_POOL_PATCH_TARGETS`), which has no such ceiling. **If `patch_get_pool` ever needs another entry, add it to the list — do not revert to a parenthesized `with (...)` block.**
- **Shared `dba_test` Postgres DB's alembic version can silently drift when multiple worktree agents run pytest concurrently.** Each worktree's `conftest.py` runs `alembic upgrade head` from its own on-disk migration files against the one shared DB; if a worktree lacking a newer migration runs after one that has it, later test runs can find themselves below the migrations the merged code actually expects, producing confusing `KeyError`s on columns that "should" exist. Check `docker exec dba-db-1 psql -U dba -d dba_test -c "SELECT version_num FROM alembic_version;"` against `alembic heads` if a merge's tests fail with unexplained missing-column errors right after a multi-worktree session.
- **Docker Postgres (`dba-db-1`) shows real flakiness under concurrent/heavy test load** — deadlocks on the `clean_db` autouse fixture's `TRUNCATE ... CASCADE` colliding with in-flight test inserts, and the container itself crashed/restarted more than once during this session's work. Confirmed via `git stash` A/B testing by two independent agents that this is NOT caused by any code change — it reproduces on unmodified files too. A single sequential test run is clean. Worth a real look (e.g. faster volume, or serializing `clean_db`) if concurrent test runs against this DB become routine.
