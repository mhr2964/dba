# Architecture — DBA

Layered-monolith Python/discord.py/PostgreSQL Discord bot simulating an NBA fantasy league.

## Layers

| Package | Role |
| --- | --- |
| `bot/` | Discord-facing layer: `cogs/` (16 slash-command groups), `embeds/` (18 embed builders), `ui/` (5 interactive views/modals), `client.py` (bot bootstrap) |
| `services/` | Business logic: 45 top-level modules + `personas/` (20, columnist voice/prompt definitions), `philosophies/` (9, coaching-bias role-assignment modifiers), `trade_signals/` (10, trade-context signal providers) |
| `data/` | Persistence: `db.py` (asyncpg pool), `repositories/` (25 modules, one per aggregate — the only place raw SQL should live), `seeds/`, cached rating/stat snapshots (`2k_ratings/`, `bdl_cache/`, `stats_ratings/`, `tendency_cache/`) |
| `core/` | Cross-cutting: `config.py` (fail-fast required env vars), `errors.py`, `logging.py` |
| `phase/` | Season-phase state machine: `states.py`, `transitions.py`, `guards.py`, `helpers.py` |
| `alembic/` | 45 migrations, linear `down_revision` chain from `001` through `045` |
| `tests/` | pytest + pytest-asyncio, 253 tests (242 passing, 10 `xfail`, 1 integration-marked skip as of 2026-07-22) |
| `scripts/` | Durable CLI utilities (seed builders, rating fetchers, `purge_dba.py`, `query_db.py`) — one-off diagnostic/backfill scripts are not kept here; they're disposable once their fix has shipped |

## Invariants

- **`services/` never imports `discord`.** As of 2026-07-22, 10 of the ~91 service files still do (`batch_sim_runner.py`, `cpu_trade_service.py`, `draft_service.py`, `fa_service.py`, `feedback_log.py`, `import_service.py`, `league_service.py`, `news_router.py`, `notifier_service.py`, `playoff_service.py`) plus the two announcer adapters where it's expected (`cpu_trade_announcer.py`, `sim_channel_announcer.py`). Business logic should return plain payload dataclasses; posting to Discord is a presentation concern. `grep -rn "^import discord\|^from discord" services/` is the check — not yet clean, enforced incrementally as Phase 2 extractions land.
- **`data/repositories/` owns all SQL.** Raw `pool.fetch*/execute` calls scattered through `services/` should move into a repository module as each is touched. `grep -rn "pool\.\(fetch\|fetchval\|fetchrow\|execute\)" services/` is the check — same incremental enforcement as above.
- **`Announcer` protocol** (`services/announcer_protocol.py`) is the seam between business logic and Discord posting: `post_embed(channel_key, EmbedData)`, `post_text(channel_key, content)`. `channel_key` is the same string already passed to `league_repo.get_channel(pool, league.id, channel_key)` (e.g. `"trade-block"`) — this formalizes an existing convention rather than inventing a new one. `EmbedData` is a plain dataclass (title/description/color/fields/footer/thumbnail_url/image_url) covering the field usage seen across current `discord.Embed(...)` call sites. Every extraction in Phase 2 that currently posts directly to a channel implements or consumes this instead of importing `discord` itself; concrete adapters (`cpu_trade_announcer.py`, `sim_channel_announcer.py`) are added as part of that split, not before.

These two invariants are the organizing principle behind the two-largest-files split (`services/cpu_trade_proposals.py`, 4,274 LOC — split 2026-07-22; `services/batch_sim_runner.py`, 3,653 LOC — in progress) — see the re-architecture plan referenced in `HANDOFF.md` for the current split status, and `trade-logic-rules.md` for the trade-evaluator behavior those files implement.

## Split status

- **`cpu_trade_proposals.py` (4,274 LOC) — done, 2026-07-22.** Became 6 files: `trade_gates.py` (207 LOC, `_apply_final_trade_gates`), `trade_proposal_scoring.py` (538 LOC, pure scoring/routing helpers), `trade_return_builder.py` (520 LOC, return-package assembly), `trade_block_builder.py` (142 LOC, trade-block derivation), `cpu_trade_announcer.py` (102 LOC, the only file here allowed to `import discord` — implements `Announcer`), and `cpu_trade_proposal_runner.py` (2,891 LOC — the slimmed orchestration core: mode dispatch, candidate search, the CPU-to-CPU auto-approve transaction). Extraction was a byte-accurate line-slice, not a retype — zero behavior change, verified by full-suite re-run (242 passed/10 xfailed/1 skipped, unchanged) plus a direct import of all 6 modules. `cpu_trade_proposal_runner.py` is still 2,891 LOC by design: it retains `_run_incoming_first_for_team` (~1,480 LOC), which the plan explicitly calls out as currently zero-coverage — **do not refactor that function's internals without adding characterization tests first**; relocating its call-site imports (what this pass did) is safe, rewriting its logic is not.
- **`batch_sim_runner.py` (3,653 LOC) — partially split, 2026-07-22.** Two new modules extracted so far:
  - `sim_persistence.py` (543 LOC): the 9 pure roster/lineup/role-cache helpers (`_ensure_lineup`, `_compute_team_ovr`, etc. — zero `discord`, confirmed by grep before moving), plus `_persist_game_result` and `_persist_injuries`. The latter two were **not** pure — they interleaved DB writes with inline `discord.Embed` construction (injury alerts, win-streak/record embeds) and had zero test coverage. Before touching them: wrote `tests/test_persist_injuries.py` (7 cases) and `tests/test_persist_game_result.py` (5 cases) as characterization tests against the *original* inline-embed code, using a recording `_FakeChannel`. All 12 passed against the original implementation. Then converted both functions to build `EmbedData`/`EmbedField` and post through `_BoundChannelAnnouncer` instead of constructing `discord.Embed` directly — the same 12 tests were re-run against the converted code and passed unchanged, byte-for-byte (embed title/description/field/footer text identical). One exception left as a direct `channel.send`: the all-time-record embed is built by the pre-existing `bot/embeds/sim_embeds.season_record_embed()` (an already-opaque `discord.Embed`-returning builder, same pattern used elsewhere in this codebase) — not something this module constructs itself, so routing it through the announcer wasn't necessary to satisfy the invariant.
  - `sim_channel_announcer.py` (126 LOC): the 6 channel-lookup helpers (`_get_box_scores_channel`, `_ensure_records_channel`, etc. — pure resolution logic, no characterization needed) plus `_BoundChannelAnnouncer`, a concrete `Announcer` that wraps an *already-resolved* channel object rather than resolving by `channel_key` per call (unlike `cpu_trade_announcer.py`). This deviates from the protocol's literal channel_key-lookup design — sim orchestration resolves each channel once per batch and threads the object through several function calls (`_sim_single_game` → `_persist_game_result` → `_persist_injuries`), and changing that threading architecture was out of scope for this pass. `channel_key` is accepted (for structural conformance) but ignored.
  Both new modules verified: ruff clean, import without circular-import errors (broke a `sim_persistence.py` ↔ `batch_sim_runner.py` cycle with a deferred local import of `_maybe_post_triage_report`, same pattern already used elsewhere in this codebase for cross-module calls), full suite green at 254 passed (242 + 12 new)/10 xfailed/1 skipped.
  - **`cpu_trade_round_trigger.py`** (470 LOC, new): `_maybe_run_cpu_trades`, `_run_cpu_trades_inner`, `_is_blockbuster_trade` — bridges sim batches to CPU trade rounds and announces the results (trade-executed/pending embed + thread, Marcus Cole blockbuster analysis). Same characterization-tests-first treatment: `tests/test_run_cpu_trades_inner.py` (7 cases, using recording fakes for the channel/message/thread objects and mocking `columnist_service.generate` + the deep context-signal chain rather than re-verifying trade-evaluation business logic) confirmed against the original inline-`discord.Embed` code first, then the conversion to `EmbedData`/`_BoundChannelAnnouncer` was verified against the same 7 tests unchanged. This conversion needed two new `_BoundChannelAnnouncer` methods beyond the base protocol: `post_embed_get_ref` (returns the sent message so `feedback_log` and thread-creation can still use it) and `create_thread_and_send` (wraps `message.create_thread(...)` + `thread.send(...)`) — threads aren't expressible in the base `Announcer.post_embed`/`post_text` shape, so this is a deliberate, documented extension rather than a protocol violation. `_interest_score_from_batch_result` (dead code — defined, never called anywhere in the codebase) and `_fetch_race_leaders_once` (used only by the still-untouched `_maybe_post_the_race` et al.) were deliberately left in `batch_sim_runner.py`, not part of this group.
  Full suite after this step: 261 passed (254 + 7 new)/10 xfailed/1 skipped. `batch_sim_runner.py` is now 2,682 LOC before the `sim_content_pipeline.py` work below began.
  - **`sim_content_pipeline.py`** (in progress, 559 LOC so far): the dozen `_maybe_post_*` columnist/report functions, moved one at a time (each: characterization tests against the original → convert to `EmbedData` → re-verify → extract → commit), since this is the largest remaining chunk (one function, `_maybe_post_columnist`, is ~825 LOC) and the most feedback-tuned part of the bot. So far: `_maybe_post_awards_races` (mechanical move, no conversion needed — it only calls the existing `bot/embeds/awards_embeds.awards_race_embed()` builder and forwards the result, same precedent as `sim_embeds.season_record_embed`), `_maybe_post_potm` (converted; `tests/test_maybe_post_potm.py`, 4 cases), `_maybe_post_coach_beat` (converted; `tests/test_maybe_post_coach_beat.py`, 4 cases — the ~50-game cadence counter `_coach_beat_game_counter` moved with it), `_maybe_post_power_list` (converted; `tests/test_maybe_post_power_list.py`, 6 cases — the rank-delta-from-previous-article parsing and the ~70-game cadence counter `_power_list_game_counter` moved with it), and `_maybe_post_rookie_watch` (converted; `tests/test_maybe_post_rookie_watch.py`, 5 cases — the ~70-game cadence counter `_rookie_watch_game_counter` moved with it). `_build_batch_game_context` (the shared minimal-context builder several remaining `_maybe_post_*` functions call) moved here too since it's a dependency of the ones already converted; `batch_sim_runner.py` imports it back for its own not-yet-moved callers. `_PERSONA_COLORS` (persona brand-color RGB tuples) and the `_rgb_to_int` helper (matches `discord.Color.from_rgb`'s formula) now exist in both `batch_sim_runner.py` (still needed by unconverted functions) and `sim_content_pipeline.py` — temporary duplication during the incremental migration, to be consolidated once every persona-color consumer has moved.
